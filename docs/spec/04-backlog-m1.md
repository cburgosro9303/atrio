# Backlog Semilla — Implementación M1

Tareas ordenadas por dependencia. Cada bloque depende de los anteriores; dentro de un bloque, las tareas marcadas ∥ son paralelizables entre sí. Los estados siguen el ciclo de vida definido (nacen en construcción; este backlog las deja `ready_for_dev` salvo indicación).

**Criterio de cierre de M1**: un desarrollador instala la CLI, ejecuta `init`, recorre el flujo de inicialización completo por CLI (etapas omitibles, agente único por etapa vía Claude Code), y obtiene un monorepo con documentación cerrada, backlog semilla, estructura de gestión y scaffold — clonable por otra persona que con `sync` retoma el estado íntegro.

## Bloque 0 — Fundaciones del repositorio

**T-001 · Bootstrap del repositorio** *(estado: **completada**)*
Módulo Go, estructura de paquetes (`core/`, `store/`, `gitops/`, `providers/`, `flows/`, `api/`, `cli/`, `web/`), linters, formateo, verificación de dependencias unidireccionales (test de imports que falla si `core` importa algo o si alguien importa `cli`/`api` — regla precisada por ADR-016 al implementarla, ver abajo).

Decisiones de cierre: módulo `github.com/cburgosro9303/atrio` (a renombrar cuando se elija la organización GitHub — sub-tarea residual de T-003; el path aparece en `go.mod`, `Makefile` y `.golangci.yml`, el rename los toca los tres); Go fijado en `1.26` sin directiva `toolchain`; `web/` aún no lleva `//go:embed`: sin build de la SPA, la directiva rompería la compilación.

**Regla de dependencias resuelta por ADR-016.** Implementar la regla como test destapó que "nadie importa `cli` ni `api`" no podía convivir con la topología de ADR-002 (el comando de portal levanta el servidor desde `cli`). Se conceden dos excepciones nominales — `cmd/atrio → cli` y `cli → api` — y ninguna más; `cmd/atrio` alcanza `api` solo transitivamente. El test separa import directo de cierre transitivo para que la segunda excepción no arrastre a la primera. **Esto desbloquea T-080**, que ya no arranca contra una regla que lo prohibía.

**Insumos para T-002**: `CGO_ENABLED=0` solo en targets de build (fuera de darwin, `-race` exige cgo); `make test` con `-count=1` porque la caché de Go no ve la salida del subproceso `go list` del que depende el test de arquitectura; usar `make fmt-check`, no `make fmt`, como puerta de CI — `fmt` muta archivos y siempre sale 0.

**T-002 · CI base** *(estado: **completada**, depende de T-001)*
Pipeline: build multiplataforma (Linux/macOS/Windows), tests con `-race`, lint. Matriz de cross-compile desde el día uno para detectar dependencias que la rompan (p.ej. CGo accidental).

Decisiones de cierre: GitHub Actions como proveedor (`.github/workflows/ci.yml`) — no estaba nombrado en ninguna espec, se elige por coherencia con ADR-009, que ya fija GitHub Releases como canal de distribución. Tres trabajos: `quality` (fmt-check, vet, lint y comprobación de `tidy`, un solo runner), `test` (suite con `-race` en ubuntu/macos/windows, `fail-fast: false`) y `cross-compile`. Disparadores: `push` a `main` y a `task/**` y `bug/**` —así una tarea obtiene su evidencia antes de proponerse— más `pull_request`.

**Matriz ratificada.** La lista `linux/amd64, linux/arm64, darwin/amd64, darwin/arm64, windows/amd64` queda confirmada como la matriz oficial, y `PLATFORMS` del Makefile como su única definición: el trabajo de cross-compile invoca `make build-all` en lugar de reescribir la lista en YAML, de modo que no existe una tercera copia que pueda derivar. El comentario del Makefile que remitía a T-002 como fuente autoritativa se invierte en este mismo cambio.

**`internal/citest`.** El paso de tests no puede llamar a `make test` (no hay GNU make en el runner de Windows), así que deletrea el comando — y esa copia a mano es justo la clase de deriva que el proyecto sincroniza con un test, no con un comentario. El paquete nuevo impone dos reglas leyendo Makefile y workflow como texto, sin dependencias añadidas. Primera: el comando del paso `Race suite` debe ser idéntico al recipe del target `test` — quitar `-race` o `-count=1` de cualquiera de los dos rompe el test. Segunda, enunciada en ambas direcciones: el paso de cross-compile debe invocar `make build-all` **y** el workflow no puede nombrar ninguna plataforma de `PLATFORMS`; solo prohibir los nombres dejaría pasar el caso más ruidoso, borrar el trabajo entero. Todo falla en cerrado: paso renombrado, recipe ausente o `run:` convertido a escalar de bloque abortan en vez de pasar en vacío. Verificado contra diez escenarios de deriva en una copia desechable, incluida la revisión cruzada del `code-reviewer`.

Otras decisiones dentro del alcance: acciones ancladas por SHA de commit (una etiqueta se puede mover, un SHA no) con `.github/dependabot.yml` acotado a `github-actions` para que los anclajes no se pudran — el ecosistema `gomod` se deja fuera a propósito, la dependencia de linter arrastra unos doscientos módulos indirectos. `permissions: contents: read` en la raíz del flujo: nada aquí publica. El trabajo de tests llama a `go test` directo en vez de `make test` porque el runner de Windows no trae GNU make (sí trae gcc 15.2, que es lo que `-race` necesita allí); las tres patas ejecutan el mismo comando. Se añade la comprobación de `go.mod`/`go.sum` limpios tras `make tidy`: la deriva ahí es por donde entra una dependencia sin revisar.

Pendiente heredado: el gate del invariante de almacenes (T-023) se suma al trabajo de tests cuando exista; hoy no hay nada que ejecutar. No se toca firma de binarios ni provenance: no hay requisito en ninguna espec y su lugar natural es T-081.

**T-003 ∥ · Decisión de nombre del producto** *(estado: **resuelta** — ADR-015)*
Nombre: **Atrio**. Comando `atrio`, carpeta `.atrio/`, base local `atrio.db`. Sub-tarea residual antes del primer release público: validación de marca y elección de organización GitHub distintiva (colisión conocida: Atrio Inc./atrio.io).

## Bloque 1 — Contratos de datos

**T-010 · JSON Schemas literales de artefactos** *(estado: **completada**)*
Tarea, decisión, entrada de bitácora, changelog, configuración de proyecto, declaración de agentes/personalización/permisos, progreso de flujo, front-matter documental. Incluye `schemaVersion` en todos y las reglas de validación especiales (estados definitivos inmutables, `artifactLanguage` inmutable, `blockedBy` obligatorio en bloqueada, unicidad de `displayName`).

Los nueve archivos viven en `schemas/` (paquete hoja, embebido con `go:embed`), con `README.md` como contrato legible y la tabla de qué valida el esquema y qué valida el código. La spec fijaba los campos pero casi ninguna convención; estas son las decisiones de cierre.

**Convenciones.** Draft **2020-12** —no es preferencia: la envolvente se compone con `allOf` y cada artefacto se cierra con `unevaluatedProperties: false`, combinación que draft-07 no permite—. `$id` **relativo** e idéntico al nombre del archivo: Atrio no tiene dominio propio todavía (ADR-015) y un `$id` absoluto sería una URL que el proyecto no controla; publicarlos bajo una base en T-082 no exigirá tocar los archivos. `schemaVersion` **entero** monótono por tipo, inferido de la aritmética `N`/`N-1`/`N-2` de la ventana de compatibilidad. Ningún campo desconocido pasa.

**Idioma del contrato (decisión del usuario).** La spec escribía los valores en dos idiomas —`ready_for_dev` en inglés, `completada`/`activa`/`en_curso` en español, y los subcampos de `stateHistory` como `{de, a, quién, cuándo, motivo}` con tildes—. Se congela **todo en inglés**: el español de la spec es prosa descriptiva, no elección de identificador, `ready_for_dev` era ya la única forma fijada en backticks, y CLAUDE.md manda que el bilingüismo llegue por i18n y no por traducción de código. Además saca las tildes de un contrato público.

**Modelado dentro del alcance.** El bucle por ambiente son dos estados cerrados (`deploying`, `testing`) más `currentEnvironment`, no un estado por ambiente: así el enum sigue siendo validable mientras `environments[]` permanece mutable. La entrada de bitácora **no** redeclara `timestamp` ni `actor`: la envolvente ya los aporta como `createdAt`/`createdBy` y duplicarlos abriría la puerta a que discrepen —el resumen de arquitectura ya los omitía—. El catálogo de `eventType` se cierra en seis valores (`agent_run_started`, `agent_run_finished`, `authorization_granted`, `authorization_denied`, `milestone`, `note`); la spec solo daba el de autorizaciones como ejemplo. El front-matter lleva una **envolvente reducida** (`schemaVersion`, `id`): fechas y autoría a mano en un markdown se pudren contra git, que ya las sabe. No se inventaron campos que la spec no menciona —estimación, prioridad, criterios de aceptación—: añadirlos después es aditivo y seguro; quitarlos de un contrato congelado, no. El patrón de `branch` queda deliberadamente laxo porque la longitud del ulid-corto la fija T-031.

**Contradicciones resueltas.** *Front-matter*: ADR-005 descarta YAML y ADR-014 no declaraba serialización — se resuelve con **ADR-017**, que acota (no rompe) ADR-005 al bloque de front-matter y valida la forma ya parseada. *Progreso de flujo*: `03-arquitectura.md:39` lo lista en el almacén JSON versionado pero el árbol de `:47` no lo nombra — se trata como omisión del árbol y vive en `management/flows/`. *`title` de decisión*, presente en ADR-014 y ausente del resumen de arquitectura: se incluye, ADR-014 es el listado completo.

**Pruebas.** Cada esquema compila contra el meta-esquema, cumple las convenciones (verificadas, no prometidas) y se ejerce contra sus fixtures válidas e inválidas —sin cifras aquí: un número en prosa se queda obsoleto en cuanto alguien añade una fixture, y quien las cuenta es el test—. Una fixture inválida se llama `<propiedad>--<motivo>.json` y el test no se conforma con que sea rechazada: **exige que el error apunte a esa propiedad**, recorriendo el árbol de causas del validador en vez de buscar subcadenas —una subcadena acierta por casualidad—. Esa aserción es la semilla del error reparador de T-020. Arnés probado contra seis regresiones (palabra clave inválida, `$ref` roto, `unevaluatedProperties` aflojado, `$id` desalineado, regla eliminada, esquema sin fixtures) y contra una fixture con nombre mentiroso.

**Dependencia nueva (aprobada).** `github.com/santhosh-tekuri/jsonschema/v6 v6.0.2`, Apache-2.0, Go puro sin CGo. Ya estaba en el grafo del módulo como dependencia indirecta del linter, así que promoverla a directa **no añade ningún módulo al build**: `go.sum` no cambia.

**Herencia para T-020.** Cuando falla un campo de la envolvente, el error real llega acompañado de una cascada de `false schema` sobre el resto de la envolvente —efecto de que la rama `allOf` fallida pierde sus anotaciones bajo `unevaluatedProperties`—. El error reparador debe quedarse con la causa más específica del árbol, no aplanar la lista.

**T-011 ∥ · JSON Schema del manifiesto del marketplace** *(estado: **completada**)*
`manifestVersion`, items con `type: agent|skill|pack|flow`, descripciones `{es,en}`, `requiredCapabilities`, checksums. **API pública: revisión extra antes de congelar.** El esqueleto completo se revisó campo por campo antes de escribirlo; lo que sigue son las decisiones de cierre.

**Una tercera familia de esquema.** El manifiesto no es un artefacto de proyecto: lo publica el repositorio de definiciones por tag, así que no tiene ULID ni identidad git que atribuirle, y la spec le da `manifestVersion`/`platformVersion` en vez de la envolvente común. Darle la envolvente de artefacto habría exigido inventarle ambos campos, justo lo que T-010 se prohibió. Se añade `manifestEnvelope` a `common.schema.json` —con `manifestVersion` como `$ref` a `schemaVersion`, porque ADR-005 dice que el manifiesto sigue el mismo estándar y es la generación del esquema bajo el nombre de la API pública— y **el test se endurece en vez de eximirse**: antes bastaba llevar *una* de las dos envolventes, lo que dejaba pasar un front-matter que se declarase artefacto; ahora cada esquema lleva **exactamente una y la de su familia**, y la familia por defecto es la de artefacto, así que un esquema nuevo queda sujeto a la regla hasta que alguien decida otra cosa.

**`requiredCapabilities` se valida en código, no en el enum (decisión del usuario).** `03-arquitectura.md:66` y ADR-013 enumeran ocho capacidades y cierran con `…`: el catálogo está declarado cerrado pero la spec lo deja abierto, y quien lo cierra es T-050, que corre *después* de que este contrato sea público. Lo que discrimina no es enum contra patrón sino si la novena capacidad debe bumpear `manifestVersion`. Se elige el patrón `^[a-z][a-z0-9_]*$` más pertenencia verificada por el core: añadir una capacidad pasa a ser una release de plataforma y no un cambio incompatible de una API publicada. El precedente de `permissionCategory` —enum cerrado— no aplica: aquellas siete categorías estaban completamente enumeradas en la spec.

**Contradicciones resueltas.** *`type`*: ADR-014 lista `agent|skill|pack`, pero `03-arquitectura.md:86`, `:90` y este backlog incluyen `flow`, y §9 hace de los flujos definiciones distribuidas por el marketplace — entra `flow`, ADR-014 es la lista más vieja y estrecha. *`stage/rol`*: se lee como "uno u otro según el ítem". Se incluye `role` (obligatorio en `agent`, prohibido en el resto) y **se omite `stage`**: T-012 declara los participantes de una etapa por rol, así que el binding etapa↔rol lo posee el flujo, y la tabla de agentes M1 es el mapeo *del flujo de inicialización*, no una propiedad del agente — duplicarlo se rompería en cuanto un segundo flujo reutilizara un rol. La fixture inválida `stage--unknown-property.json` deja la decisión ejecutable.

**Modelado dentro del alcance.** `files[]` y `checksums` se funden en `files[]` de `{path, sha256}`: un checksum sin archivo, o al revés, quedan irrepresentables. `sha256` y no `checksum` —un digest sin algoritmo es una migración futura garantizada—. El `path` lleva patrón restrictivo que hace **irrepresentables** los segmentos `.` y `..`: la defensa contra traversal al materializar en `.claude/` tiene que vivir en el contrato, no en el código que lo consume. `providers` es la unión literal `"all" | [ids]` de la spec; "ausente significa todos" sería semántica implícita en el documento de mayor costo de cambio del proyecto. Un pack es composición: declara `includes[]` y no trae archivos propios, pero **sí declara** sus `providers` y `requiredCapabilities` en vez de derivarlos, para que una card del marketplace no tenga que calcular uniones — la coherencia con sus miembros la verifica el core. `description` es un mapa abierto ISO 639-1 con `es` y `en` obligatorios, alineado con `artifactLanguage`: un tercer idioma pasa a ser dato del catálogo, no cambio de contrato. **Sin versión por ítem**: las definiciones se versionan por el tag que las publica (`01:77`, T-061 cachea por versión), así que la referencia de un proyecto es este `id` unido al `platformVersion` del manifiesto; añadir un campo opcional después es aditivo y seguro, congelarlo hoy sin necesidad no.

**Dos esquemas de T-010 tocados, a propósito y por la convención de un solo sitio por concepto.** `platformVersion` de `project-config` pasa de patrón en línea a `$ref` —cambio puro de referencia, cero cambio semántico—. El identificador de proveedor se estrecha a `providerId` en `project-config.providers[].id` y en las claves de `personalization.providerSettings`: antes era cualquier cadena no vacía, y un typo ahí direccionaba silenciosamente a un proveedor inexistente. `catalogId` se extrae para que el manifiesto nombre un ítem sin versión, y **un test exige que siga siendo el prefijo literal de `catalogRef`**: si derivaran, el manifiesto podría publicar un ítem legal que ningún proyecto puede referenciar.

**Pruebas.** Fixtures válidas e inválidas como en T-010, con la advertencia heredada respetada: una causa que solo aparece en la cascada de `unevaluatedProperties` no localiza nada, así que las inválidas rompen reglas que producen causa sustantiva o cuya única causa es la del campo que nombran. Arnés verificado contra diez regresiones en una copia desechable —manifiesto con envolvente de artefacto, artefacto con envolvente de manifiesto, esquema con dos envolventes, `catalogId` ensanchado, patrón de `path` aflojado, las dos reglas condicionales de `role` y `files` aflojadas, ítem abierto, fixture con nombre mentiroso y esquema nuevo sin fixtures—: las diez fallan.

**Herencia para T-060/T-061.** El manifiesto declara y no deriva, así que T-061 arrastra cinco reglas que este esquema no puede expresar —unicidad del `id` de ítem, resolución de `includes[]`, cobertura de un pack sobre sus miembros, digest contra archivo descargado y unicidad del `path` dentro de un ítem—; T-050 arrastra una sexta, la pertenencia al catálogo de capacidades. Las seis están en la tabla del `README.md` de `schemas/`. La del `path` la destapó la revisión: `uniqueItems` solo rechaza entradas idénticas, así que dos con la misma ruta y distinto digest pasaban, dejando implícito cuál vale; y la misma comprobación tiene que ignorar la caja, porque dos rutas que solo difieren en mayúsculas colisionan al materializar en macOS o Windows. Es exactamente el hueco que T-010 ya había documentado para el `id` de etapa de un flujo, y se cierra igual: en el código, no fingiendo que el esquema puede.

**T-012 ∥ · Esquema de definición canónica de agente y de flujo declarativo** *(estado: **completada**)*
Formato agnóstico de agente (incluida la sección de personalización delimitada) y formato de flujo (etapas, participantes por rol, entradas, salidas con esquema, omitibilidad, checklist de datos bloqueantes). Se revisó en dos rondas —agente primero, flujo después— porque una sola aprobación sobre dos contratos públicos es peor revisión que dos.

**Cuarta familia de esquema.** Una definición canónica no es artefacto de proyecto ni es el manifiesto: la publica el repositorio de definiciones y, a diferencia del manifiesto, **no lleva versión propia** — la versión de una definición es el tag que la publica, y el manifiesto de ese tag es lo que une este `id` a una versión. De ahí `definitionEnvelope` (`schemaVersion`, `id` del catálogo). El endurecimiento de T-011 se extendió sin maquinaria nueva: dos entradas más en la tabla de familias.

**Instrucciones en markdown referenciado (decisión del usuario).** ADR-013 fija "formato propio JSON, compilado por cada adaptador"; se lee como que el *formato de definición* es JSON —frente a mantener N formatos nativos— y no como que cada byte viva dentro del JSON. Lo que decide no es ADR-013 sino T-052: la comparación tres vías y el `adoptar` de R7 operan sobre el archivo materializado, y un diff sobre una cadena JSON con saltos escapados no lo lee nadie. La definición nombra el archivo del cuerpo; el punto de inserción de la personalización es un `anchor` que el adaptador sustituye al compilar, y los delimitadores del archivo compilado son del dialecto nativo, no de este contrato.

**La definición declara, el manifiesto indexa.** T-060 genera el manifiesto desde las definiciones. Al construir el esquema de flujo se destapó que la dirección no se sostenía: `name` y `providers` del manifiesto **no eran derivables** de ninguna definición. Se añaden a ambas —`name` es el nombre del catálogo (`Architect`), distinto del `defaultDisplayName` de persona (`Andrés`)— y `providerScope` sube a `common`. No contradice lo decidido en T-011 para los packs, que sí declaran lo suyo: un pack no tiene archivo de definición, su entrada del manifiesto **es** su definición.

**El flujo, contra `flow-progress` congelado.** Tres acoplamientos verificados y no supuestos. `stageId` y `roleId` suben a `common` y los referencian los dos documentos. Esto **estrecha de verdad** un contrato que T-010 ya había congelado —de `{string, minLength 1}` a patrón kebab, así que un documento con `role: "Business Agent"` que antes validaba ahora no—; el riesgo práctico es nulo porque no hay tag publicado, y se comprueba que las fixtures congeladas ya lo cumplían, pero es un estrechamiento y no una mudanza. El tercero era real: `outputRefs` de una etapa cerrada son `reference`, cuyo enum no incluye la configuración, pero el mínimo bloqueante de la etapa 3 aterriza en `config.json`. Se resuelve sin ensanchar nada: la salida de esa etapa es el **documento** de análisis técnico y la escritura en configuración es efecto de la extracción, transportado por el checklist de datos bloqueantes que escribe T-071.

**Lecturas confirmadas por el usuario.** `inputs` "vía índice" describe *cómo el motor recupera* los documentos, no el selector: una etapa nombra etapas previas y, opcionalmente, etiquetas —que es lo que el índice de T-022 sabe consultar, y por donde entra el documento que aporta el usuario en T-073—. `blockingDataKey` lleva patrón y no enum, con la pertenencia como regla de código: mismo trade-off que `requiredCapabilities`. Fuera del contrato queda el moderador con agenda, que es de M2 y tiene fixture inválida que lo deja ejecutable; `participants: []` es la forma de decir que una etapa es determinística, que es lo que el scaffold es.

**Defecto encontrado y cerrado: `propertyNames` no localiza.** Escribiendo la fixture de una clave inválida el test falló, y el volcado del árbol de errores del validador mostró la causa: `propertyNames` reporta con la **ubicación de instancia vacía en todos los niveles**, así que el campo culpable no viaja en el error y el rechazo no puede decir qué reparar — exactamente lo que el README promete que no pasa. Cuatro sitios lo usaban (`localizedText` y el `providerSettings` de `agents.json`, ambos de T-011; el de esta tarea; y `schemaVersions` de T-010), y **ninguna fixture, desde T-010, ejercitaba jamás una clave inválida**: por eso llevaba tres tareas escondido. Los cuatro pasan a `patternProperties` + `additionalProperties: false`, que restringe lo mismo y falla en la ubicación del mapa; un test prohíbe `propertyNames` a cualquier profundidad y otro mantiene iguales los patrones que quedan duplicados por ser claves de regex, que no admiten `$ref`. Se añadieron las cuatro fixtures que faltaban.

**Otras extracciones a `common`.** `languageCode` (estaba en línea en tres sitios), `artifactType` (estaba en línea dentro de `reference`) y `definitionPath` — el patrón anti-traversal de T-011, que ahora existe **en una sola copia** en vez de duplicarse entre el manifiesto y la definición de agente: una regla de seguridad duplicada es una regla que se pudre.

**Pruebas.** La fixture válida principal del flujo es el **flujo de inicialización de M1 completo**, con sus cinco etapas y sus ids coincidiendo con los de las fixtures de `flow-progress`: la prueba de que el esquema expresa lo que la tarea existe para expresar. Arnés verificado contra seis regresiones en copia desechable —vuelta a `propertyNames`, `propertyNames` escondido dentro de un `allOf`, clave de patrón derivando de `common`, definición con envolvente de artefacto, patrón anti-traversal aflojado y `localizedText` dejando de exigir inglés—: las seis fallan.

**Lo que destapó la revisión.** `roleId` es el tercer vocabulario abierto por patrón de esta tarea, y era el único sin fila en la tabla de reglas de código: nada ata el rol que un progreso registra a los que su etapa declara. La fila faltaba y el hueco no era teórico —las fixtures congeladas de `flow-progress` registraban `business-agent` en la exploración, rol que no existe en el catálogo de `03-arquitectura.md:130-137`, y `product-owner` en la planificación, que contradice a `project-manager` y a la regla de un agente por etapa de M1—. Se añade la fila y se corrigen los tres valores, con lo que el corpus entero concuerda con el catálogo canónico. Además, el test que ata los patrones duplicados deja de ser una lista de sitios a mano y pasa a barrer el corpus entero: un mapa nuevo con clave de patrón queda cubierto solo, y una exención que sobreviva al mapa para el que se escribió también falla. La única exención viva es `schemaVersions`, cuyas claves son deliberadamente un espacio más ancho que el enum de `artifactType`.

**Herencia para T-050, T-060 y T-070.** Diez reglas nuevas que el esquema no puede expresar están en la tabla del `README.md` de `schemas/`, entre ellas que el `anchor` aparezca exactamente una vez en el cuerpo (T-052), que `inputs.stages` nombre etapas anteriores del mismo flujo (T-070) y que el manifiesto coincida con las definiciones de las que se genera (T-060).

## Bloque 2 — Capa de persistencia (`store/`)

**T-020 · Repositorio de artefactos JSON** *(estado: **completada**, depende de T-010)*
Lectura/escritura con validación contra esquema, un archivo por entidad, IDs ULID, atribución `createdBy` desde identidad git. Rechazo/marcado de artefactos inválidos con error reparador (campo, formato).

El paquete `store/` cubre los siete tipos que la tabla de `schemas/README.md` ata a una ruta dentro de un proyecto: `task`, `decision`, `log-entry`, `changelog` y `flow-progress` con un archivo por ULID bajo `.atrio/management/`, más `project-config` y `agents` como singletons en `.atrio/config.json` y `.atrio/agents.json`. Documentos genéricos (`Document = map[string]any`): modelar la forma de negocio completa como tipos Go es de `core/` (T-040) y de quien consuma este repositorio después (T-070/T-080), no de la capa de persistencia.

**Dependencia nueva (aprobada por el usuario): `github.com/oklog/ulid/v2 v2.1.2`**, MIT, Go puro. A diferencia de la promoción de `jsonschema` en T-010, esta **sí** añade un módulo a `go.sum` (más una línea de checksum de `go.mod` de `github.com/pborman/getopt`, dependencia de test transitiva de `ulid` que nunca se compila). Se usa `ulid.Monotonic` envuelto en `ulid.LockedMonotonicReader`: la entropía monótona es lo que hace que dos artefactos creados en el mismo milisegundo sigan ordenando estrictamente, y el lock es lo que hace seguro compartir un generador entre llamadas concurrentes — `log-entry.schema.json` promete explícitamente que el orden de directorio es orden cronológico, y esa promesa depende de las dos piezas juntas, no de una sola.

**Error reparador.** `explainValidation` (`store/validate.go`) recorre el árbol de causas del validador con la misma partición que T-010 dejó resuelta en `schemas/schemas_test.go` (`surveyCauses`/`locatesProperty`): separa causas sustantivas de la cascada `false schema` que arrastra un fallo de envolvente bajo `unevaluatedProperties`, y se queda con las sustantivas cuando existen. La diferencia con el test es de dirección — el test ya sabe qué campo espera y comprueba que aparezca; `explainValidation` no sabe nada de antemano y tiene que **nombrar** todos los campos rotos —, así que `Required` y `AdditionalProperties` se desempaquetan en un `FieldError` por nombre en vez de uno por regla. La misma forma de error (`ArtifactValidationError{Path, []FieldError{Field, Reason}}`) se reutiliza para las reglas de código: `artifactLanguage` cambiado, `displayName` duplicado, referencia colgante, intento de reescribir una entrada de bitácora. Un rechazo nunca es un volcado del validador.

**`AssertFormat` activado, verificado contra el corpus congelado.** Los esquemas declaran `"format": "email"` y `"format": "date-time"` (ambos solo en `common.schema.json`, sin `pattern` de respaldo), pero la aserción de formato está apagada por defecto en la librería para draft 2019-09+, y `schemas/schemas_test.go` compila con la configuración por defecto — ninguna fixture de T-010/T-011/T-012 se validó nunca con aserciones de formato activas, y esa suite no comprueba en absoluto si `createdAt`/`updatedAt` son una fecha real o si un email lo es. `store` es quien realmente hace de puerta de escritura, así que `compileSchemas` (`store/validate.go`) llama a `compiler.AssertFormat()`. Antes de apoyarse en la decisión se comprobó que no estrecha el contrato ya congelado: `TestCompiledSchemas_AcceptEveryFrozenValidFixture` (`store/frozen_fixtures_test.go`) carga las fixtures válidas de `schemas/testdata/` para los siete esquemas que este paquete gestiona y exige que sigan validando con las aserciones activas — las 27 pasan. `TestCreateTask_RejectsMalformedIdentityEmail` y `TestReadTask_RejectsMalformedCreatedAt` dejan la propia decisión con regresión, una por cada campo que depende solo de `format`: sin `AssertFormat`, una identidad con email roto o un `createdAt` como `"yesterday"` se escribirían/leerían como si nada. **`schemas/README.md` queda anotado con esta misma decisión** —que la aserción de `format` es opt-in por consumidor, que hoy solo `store` la activa y que un consumidor futuro que compile estos esquemas por su cuenta (`flows/`, `api/`) hereda el mismo hueco si no la activa— porque el README es el contrato legible que el proyecto designa como tal, y un comentario de código o una línea de este backlog no viajan con él.

**Integridad referencial: la línea exacta.** La tabla de `schemas/README.md` reparte la regla entre este paquete y T-022. Este paquete resuelve, por existencia de archivo dentro de `.atrio/management/`, únicamente los campos tipados como `common.schema.json#/$defs/reference` (`{type, id}`): `decision.refs[]`, `log-entry.refs[]`, `changelog.impacts[]` y `flow-progress.stages[].outputRefs[]`. Un `type: "document"` se salta a propósito — apunta a `docs/**/*.md`, y si ese id resuelve a un documento indexado lo sabe el índice documental de T-022, no un `stat`. Dos campos que a primera vista también son referencias se dejan fuera **citando el propio contrato, no por categoría**: `changelog.taskRefs[]` es un array de ULID desnudo (no `reference`) y su descripción en `changelog.schema.json` asigna la resolución explícitamente "al core"; `task.blockedBy[].ref`, `task.originTaskRef` y `task.changelogRefs[]` son igual de desnudos y no llevan ninguna asignación equivalente en la tabla — se dejan para quien primero los necesite (T-040) en vez de inventar una regla que la spec no pidió.

**Dos reglas de código dentro de un mismo documento.** `artifactLanguage` inmutable (`store/project_config.go`) se decide comparando `existing.getString("artifactLanguage")` contra la versión entrante, solo cuando ya existe una versión anterior — la primera escritura no compara con nada. Unicidad de `displayName` (`store/agents.go`) recorre `agents[].personalization.displayName` dentro del mismo documento entrante; ninguna de las dos toca `core/`.

**Escritura segura.** Todo write pasa por temporal-y-rename (`writeReplacing`, `store/fsio.go`): el archivo temporal se escribe, se hace `fsync` y se cierra antes de que exista cualquier nombre final, así que un proceso que muere a mitad deja como mucho un archivo temporal huérfano, nunca uno truncado en la ruta que alguien lee. Para la bitácora (append-only) no basta con eso — `rename` reemplaza el destino si ya existe, en todas las plataformas que soporta Go —, así que `writeNew` usa `os.Link` como ruta primaria: falla atómicamente con "file exists" en vez de sobrescribir en silencio, y sigue siendo el primitivo más fiable en NFS antiguo. Como no todos los sistemas de archivos soportan enlaces duros (FAT32/exFAT, algunos recursos de red), un fallo de `Link` que no sea `ErrExist` cae a una **segunda ruta atómica** en vez de a `stat`+`rename`: reclamar `path` con `os.OpenFile(..., O_CREATE|O_EXCL|O_WRONLY, ...)`, que o bien gana el nombre o falla con `ErrExist` — sin hueco entre observar y actuar para que dos escritores concurrentes pasen ambos el `stat` — y solo entonces renombrar el temporal sobre el hueco ya reclamado. `O_EXCL` lo soportan tanto FAT32/exFAT como todo lo demás, así que la reapertura de la ventana de carrera que el `stat`+`rename` original habría dejado ya no ocurre. La ruta de `os.Link` se inyecta por variable de paquete (`linkFile`) precisamente porque en CI corre siempre sobre ext4/APFS/NTFS, donde `Link` nunca falla: sin la inyección, la ruta de repliegue tendría cobertura cero en las tres plataformas — `TestWriteNew_FallsBackWhenLinkIsUnsupported` y `TestWriteNew_FallbackRefusesExisting` (`store/fsio_test.go`) fuerzan el fallo y ejercitan tanto el camino feliz como la colisión.

**`Create`/`Update`/`Write` releen lo que acaban de escribir.** Se descubrió durante el desarrollo que el documento construido en memoria y el que decodifica un `Read` posterior no son el mismo tipo Go: `jsonschema.UnmarshalJSON` decodifica objetos anidados como `map[string]any` puro y números como `json.Number`, mientras que el documento en memoria podía llevar `Document` (tipo con nombre, para los métodos `clone`/`getString`) y `int`. Una aserción de tipo que funciona contra el documento recién creado fallaba en silencio contra el mismo documento releído más tarde. Se resolvió en dos frentes: `plainValue` (`store/document.go`) normaliza recursivamente antes de validar — el propio validador de `jsonschema` ya fallaba con `"invalid jsonType store.Document"` en valores anidados, que es como se destapó el problema —, y cada `create`/`update`/`writeSingleton` relee el archivo del disco antes de devolver el documento, así que lo que se devuelve es exactamente lo que un `Read` posterior devolvería. Esa propiedad de fallo-cerrado —un valor Go que `plainValue` no normaliza (su rama por defecto lo deja pasar tal cual) tiene que hacer que el validador de `jsonschema` falle con `"invalid jsonType"` en vez de aceptarlo en silencio— es comportamiento de una librería de terceros, no algo que este paquete controle, así que queda fijado con un test de regresión explícito: `TestUnrecognizedGoValue_FailsValidationLoudly` (`store/document_test.go`) escribe un `complex128` en un campo y exige que el rechazo nombre el campo y mencione `"invalid jsonType"`. Si una versión futura de la librería relajara esa garantía, el aviso tiene que ser un test en rojo, no un artefacto inválido escrito en disco.

**`stampUpdate` diverge, a propósito, de la convención publicada.** `schemas/README.md` dice que la versión `N` "siempre escribe `N`", pero `stampUpdate` (`store/repository.go`) arrastra el `schemaVersion` que ya había en disco en vez de restamparlo a `currentSchemaVersion`. Restampar como generación actual un documento que este paquete no ha migrado de verdad sería mentir sobre su procedencia — este paquete no implementa migración —, así que se prefiere la divergencia honesta a la convención literal. Hoy es invisible porque los siete esquemas siguen en su primera generación; el disparador que obliga a reconciliarlo es la primera vez que exista una segunda generación real de alguno de ellos, o que aterrice la lógica de migración (esqueleto en T-081). Anotado también junto a la función en el código.

**Concurrencia: qué garantiza el paquete y qué no.** Un `Repository` es seguro de usar desde goroutines concurrentes en su propio estado (esquemas compilados, generador de ids). Lo que no ofrece es serialización entre dos escrituras al *mismo* artefacto: `createArtifact` asigna un id nuevo por llamada, así que dos `Create` concurrentes no colisionan, pero `updateArtifact` y `writeSingleton` son lectura-modificación-escritura sin lock — dos `WriteProjectConfig` concurrentes pueden leer la misma versión y competir por cuál gana. Los locks son responsabilidad nombrada de T-021 en el backlog; este paquete no la inventa por adelantado.

**Fuera de alcance, y por qué.** `document-front-matter.schema.json` no tiene ruta de archivo propio dentro de un proyecto —vive como cabecera YAML de cada `docs/**/*.md`— y su parseo es T-022 por nombre ("Parser de front-matter"). `marketplace-manifest`, `agent-definition` y `flow-definition` no son artefactos de un proyecto: los publica el repositorio oficial de definiciones (T-060/T-061), no `.atrio/`. SQLite, índices, FTS y locks son T-021; el indexador documental es T-022; máquinas de estado, transiciones legales y expansión de permisos son T-040/T-041 — no se importa `core/` en esta tanda porque sus predicados no existen todavía en la forma que un consumidor necesitaría, y cablearlos es de T-070/T-080. `changelog` no lleva `Update`: la spec lo genera una vez por push (T-032); añadirlo es aditivo si hiciera falta. `schemaVersion` se escribe fijo en `1` — todos los esquemas están en su primera generación y no hay migración real que ejercitar todavía.

**Pruebas.** `go test -race ./store/...`: round-trip de los siete tipos; ULID bien formado y ordenable cronológicamente (incluso con 200 ids seguidos); `createdBy` desde una identidad inyectada, y propagación del error si esa identidad falla; rechazo nombrando el campo exacto para reglas de esquema (requerido, enum, propiedad desconocida, condicional `if`/`then`) y para las de código (`artifactLanguage`, `displayName`, referencia colgante); envolvente rota (`createdAt` ausente, `createdAt` con un valor que no es una fecha real) sin que la cascada de `unevaluatedProperties` contamine el resto de campos; intento de reescritura de una entrada de bitácora forzando una colisión de id vía el generador inyectable, en la ruta primaria de `os.Link` **y** en la de repliegue con `O_EXCL` forzando el fallo de `linkFile`; JSON corrupto, truncado y con un array en la raíz; archivo ausente; id mal formado rechazado antes de tocar el filesystem (defensa contra *path traversal*); un valor Go sin representación JSON rechazado por nombre en vez de colado en silencio. `internal/archtest` sigue en verde: `store/` solo importa `schemas/` del módulo. Cross-compile manual verificado además para `windows/amd64` — `make build-all` todavía no llega a `store/` porque `cmd/atrio` no lo importa.

**T-021 · SQLite local** *(estado: **completada**, depende de T-020)*
Esquema de base local: índice documental, FTS5, notificaciones, locks, sesión, hashes de materialización. Bootstrap y regeneración completa desde el repo.

Dos archivos en `store/`: `localdb.sql` (el DDL, embebido con `go:embed`) y `localdb.go` (apertura, bootstrap, descarte y reconstrucción). El DDL va en un `.sql` y no en literales de Go a propósito: es el artefacto que hay que revisar en esta tarea, y en SQL se lee como SQL.

**Ubicación: `.atrio/atrio.db`. Contradicción aparente, resuelta por lectura y no por adivinanza.** `03-arquitectura.md:40` y ADR-006:70 dicen "directorio de datos de la plataforma por proyecto" —lo que sugiere una carpeta fuera del repo— pero la misma celda continúa "**en el `.gitignore` generado por `init`**", y una ruta fuera del repositorio no se puede gitignorar. La segunda cláusula resuelve la primera, y coincide con `03-arquitectura.md:47`, ADR-011 y ADR-015/T-003 ("carpeta `.atrio/`, base local `atrio.db`"). La lectura se elevó al usuario antes de escribir código, no después.

**Dependencia nueva (aprobada por el usuario): `modernc.org/sqlite v1.56.0`**, fijada por nombre en ADR-007. Añade 8 módulos (`libc`, `mathutil`, `memory`, `bigfft`, `go-humanize`, `uuid`, `go-isatty`, `go-strftime`) y, por resolución de versiones mínimas, **sube cinco que ya estaban en el grafo del linter**: `x/sys` 0.43→0.47, `x/tools` 0.44→0.47, `x/mod` 0.35→0.37, `x/sync` 0.20→0.21 y `go-isatty` 0.0.20→0.0.24 — la parte que no se anticipó al pedir la aprobación, que hablaba solo de `x/sys`. La comprobación de `tidy` limpio de T-002 la deja visible en CI de todos modos. ADR-007 pide "pinning fino": la versión queda registrada aquí y `dependabot.yml` sigue acotado a `github-actions`, así que no se mueve sola. Verificado empíricamente antes de aprobarla: SQLite 3.53.3, **FTS5 disponible**, y `go build ./store/...` limpio con `CGO_ENABLED=0` en las cinco plataformas de `PLATFORMS`.

**No hay migración, y eso es una decisión con licencia explícita.** La generación del DDL vive en el `pragma user_version` de la propia base; encontrar una que este build no escribió hace que el archivo se **descarte y se reconstruya**, nunca que se migre. Lo que lo autoriza es la letra de ADR-006: todo lo que hay aquí es derivable del repositorio **o efímero**. No se escribe "todo es derivable", que sería falso —una notificación no leída no la sabe el repositorio—; se clasifica tabla por tabla, y esa clasificación vive en el comentario de tipo de `LocalDB` **y en un test** (`TestLocalDBSchema_EveryTableIsAccountedFor`) que falla en las dos direcciones. Una tabla nueva sin clase declarada es exactamente lo que ADR-006:73 llama un dato en el almacén equivocado, y ahora no puede entrar en silencio.

**No se llama `schemaVersion`.** Ese nombre ya es de los artefactos JSON, donde gobierna una ventana de compatibilidad y una migración real. Aquí es una generación de DDL con reglas opuestas —desajuste significa tirar el archivo—, y reusar el nombre habría invitado a asumir las reglas del otro.

**Defecto encontrado y cerrado: el DSN por concatenación pierde los pragmas y escribe la base en otra ruta.** La forma obvia (`path + "?_pragma=foreign_keys(1)&…"`) parece equivalente a la URI y no lo es. Probado contra un directorio llamado `with?question`: el driver corta la ruta en el `?`, así que **la base se crea en un sitio distinto del pedido** y los pragmas se descartan sin aviso — incluido `foreign_keys`, con lo que los `ON DELETE CASCADE` del DDL dejan de disparar y se acumulan filas huérfanas en una base que nadie está mirando. `localDBDSN` construye una URI `file:` con la ruta escapada; verificado contra seis nombres de directorio (`plain`, con espacio, con `?`, con `#`, con `%`, con no-ASCII) y con la aserción de que el archivo aterriza en la ruta exacta esperada.

**Los pragmas van por conexión, no por base.** Medido, no supuesto: con `SetMaxOpenConns(4)` y dos conexiones fijadas a la vez, un `pragma foreign_keys=on` por `Exec` deja `connA=1` y `connB=0`. Una conexión del pool corriendo sin claves foráneas es un fallo silencioso con consecuencias en disco, así que los tres pragmas se adjuntan al DSN, que sí se aplica a todas. `journal_mode` es la excepción conceptual —es propiedad del archivo, no de la conexión, y sobrevive a un handle nuevo que nunca lo fijó— pero se lista en el mismo sitio para que exista un único lugar donde leerlos.

**El bootstrap es atómico, y eso es lo que permite confiar solo en la generación.** El DDL y el estampado de `user_version` van en una transacción. Verificado que SQLite los trata transaccionalmente juntos: con `rollback` quedan cero tablas y generación 0; con `commit`, las 14 que `sqlite_master` reporta —8 tablas reales, la virtual `document_fts` y las 5 sombra que FTS5 crea por su cuenta— y generación 1. Por eso `OpenLocalDB` no necesita inspeccionar las tablas: una base estampada como actual no puede estar a medias. `TestBootstrapLocalDB_IsAtomic` deja la propiedad con regresión sustituyendo `localDBSchema` —variable de paquete, inyectable como el `linkFile` de T-020— por SQL que falla a mitad.

**Dos defectos que destapó la revisión, ambos en la frontera de la ruta.** El primero era bloqueante: `localDBDSN` anteponía `/` a cualquier ruta que no empezara por `/` —pensado para la letra de unidad de Windows— y con ello convertía una raíz **relativa** en absoluta desde el raíz del sistema de archivos. `OpenLocalDB` creaba entonces `.atrio/` relativo al directorio de trabajo y le pedía al driver abrir `/relroot/.atrio/atrio.db`: reproducido, falla con `unable to open database file (14)`, y ejecutándose como root habría creado en silencio una base en un sitio que `Path()` no reporta. Se resuelve donde debía resolverse, en el único punto que ve el valor del llamador: `OpenLocalDB` hace `filepath.Abs` una vez, y directorio, DSN y `Path()` hablan del mismo archivo. El segundo: el driver crea el archivo con el modo por omisión (0644 comprobado), mientras `writeNew` de T-020 pasa `0o600` a `os.OpenFile` para cada artefacto. Aquí no hay ese control —los crea SQLite—, así que el modo se estrecha justo después de la conexión que los crea, sobre los tres archivos, y un fallo se devuelve en vez de ignorarse.

**Límite conocido, anotado y no adivinado.** Una raíz UNC de Windows (`\\server\share\…`) produce `file:////server/share/…`, y que SQLite lo resuelva de vuelta al recurso compartido **no está verificado**: el runner de Windows de CI solo ejercita una unidad local. La documentación de SQLite desaconseja de todos modos poner la base en un recurso de red, porque el bloqueo del que depende no es fiable ahí. Queda como hueco documentado en el código, no tapado con manejo sin probar — el mismo tratamiento que `internal/archtest` da a los suyos.

**La atomicidad estaba probada a medias.** `TestBootstrapLocalDB_IsAtomic` inyecta un esquema que revienta durante el DDL, con lo que el estampado de `user_version` **nunca se ejecuta**: su aserción de generación 0 sería cierta aunque el estampado no fuese transaccional en absoluto. La prosa afirmaba las dos mitades y el test forzaba una. Se añade `TestUserVersionStampIsTransactional`, que estampa y crea una tabla dentro de una transacción, hace `rollback` y exige que ni la generación ni la tabla sobrevivan. El mecanismo era real —estaba verificado a mano antes de escribir el código—; lo que faltaba era que un test lo mantuviera cierto.

**Reconstruir borra el archivo en vez de las tablas.** Ir tabla por tabla obligaría a mantener la lista al día con `localdb.sql` para siempre y dejaría atrás las tablas sombra que FTS5 crea con nombres que este paquete nunca escribió. Se borran los tres archivos que la base ocupa: `atrio.db` y los sidecars `-wal`/`-shm`. **Afirmación acotada tras comprobarla**: la primera redacción decía que borrar los sidecars evita arrancar con marcos de WAL rancios al lado, y ningún test end-to-end puede demostrarlo — SQLite descarta por su cuenta un `-wal` cuya cabecera no casa con la base, así que el resultado observable es idéntico se borren o no (verificado por mutación: quitarlos de `localDBFiles` dejaba el test en verde). Se borran igual, por higiene y porque el estrechado de permisos recorre esa misma lista, pero lo que queda atado por un test es la lista de archivos, no una consecuencia que no existe. El test cambió de nombre para no prometer lo que no prueba.

**Los sidecars de WAL rompían `gitops.Status`, y el `.gitignore` no los cubría.** Activar WAL crea `atrio.db-wal` y `atrio.db-shm` junto al archivo. Los globs que había (`.atrio/*.db`, `*.db`) no casan con ninguno de los dos —comprobado con `git check-ignore`—, así que aparecían como sin seguimiento, y T-030 pasa `--untracked-files=normal` deliberadamente para que nada quede oculto: el worktree se habría reportado sucio por archivos de la propia plataforma. Se añaden los patrones al `.gitignore` del repo (la instancia de dogfooding) y `TestGitignore_CoversWALSidecars` lo ata. **El `.gitignore` que genere `init` (T-070/T-080) tiene que llevarlos igual**; esa mitad no se puede cerrar desde aquí.

**Lo que el esquema hace cumplir por sí mismo.** Todas las tablas reales son `STRICT`: sin eso SQLite guardaría una cadena en una columna `INTEGER` tal cual, que es la clase de corrupción silenciosa que una caché derivada no puede permitirse, porque cada reconstrucción la reproduciría. El catálogo cerrado de `document_relation.kind` se repite como `CHECK` —es el único guardián que tiene una tabla que ningún JSON Schema valida—, y el borrado de un documento arrastra sus etiquetas y relaciones por cascada y su fila de búsqueda por trigger. La inserción en FTS **no** se dispara por trigger a propósito: el cuerpo del documento no existe en `document`, así que solo el indexador puede aportarlo.

**FTS5 regular, no `content=''`.** Una tabla sin contenido no produce `snippet()`/`highlight()` y exige que quien borre una fila devuelva los valores originales, lo que traslada una carga de corrección a cada consumidor futuro. El precio es que el texto indexado se guarda aquí además de en `docs/` — aceptable justo porque este archivo es derivado, está gitignorado y se descarta ante cualquier cambio de generación. El cuerpo **no** se copia a `document`: el corpus tiene su fuente de verdad en el repositorio, y la única copia que existe es la que FTS necesita para indexar.

**Tercer defecto, este de diseño: la unión con el índice de búsqueda no podía ir por `rowid`.** La primera versión ataba `document_fts` a `document.rowid` y el trigger de borrado comparaba `rowid = old.rowid`. `document` declara clave primaria **TEXT**, así que no tiene alias `INTEGER PRIMARY KEY`, y SQLite documenta que `VACUUM` puede **renumerar** los rowid de exactamente esas tablas: una orden de mantenimiento rutinaria repuntaría cada acierto de búsqueda a otro documento, en silencio y de forma permanente. La unión pasa a ser `document_id`, la misma identidad ULID que usa el resto del esquema, declarada `UNINDEXED` para que el identificador se guarde y se pueda leer sin volverse un término buscable (comprobado en aislamiento: un término presente solo en esa columna no casa con nada). Lo que destapó lo insuficiente de la prueba fue mutar el código: **`VACUUM` no renumera en esta compilación de SQLite**, así que un test que solo vacuumea deja pasar la versión rota. Lo que sí la fuerza es insertar las filas de búsqueda en orden distinto al de los documentos —nada obliga al indexador a escribirlas al unísono—: los rowid dejan de alinearse y el trigger por rowid borra la fila de otro documento. Con esa rotación, volver al trigger anterior deja el test en rojo con las dos consecuencias visibles: la fila del documento borrado sobrevive y la de un documento vivo desaparece.

**Locks: solo el registro (decisión del usuario).** `03-arquitectura.md:32` es preciso —el mutex *es* un lockfile y SQLite es donde queda registrado—, así que `project_lock` es un registro y no un mutex. Adquisición y liberación viven con el primer llamador que las necesite (T-031), junto con la política que esta tarea no tiene base para inventar: cómo se detecta un titular muerto, si un lock caduca y quién puede romperlo.

**Sin accesores por tabla (decisión del usuario).** `LocalDB` expone `DB()`, `Path()`, `Close()` y `Reset()`, nada más. La forma de cada API la conoce la tarea que consume la tabla (T-022, T-042, T-052, T-031); inventarla aquí, sin un llamador a quien responder, es el error que T-020 evitó dejando `Document` como mapa genérico. `Reset()` es la mitad de "regeneración completa desde el repo" que sí es de este paquete: descartar y dejar el esquema vacío. Repoblar es el mismo camino de código que la construcción inicial, no una segunda implementación de ella, así que es de quien la escribió.

**Fuera de alcance, y por qué.** La línea de la tarea nombra exactamente seis cosas y se implementan esas seis. ADR-006:70 lista además dos que no entran: el **consumo de tokens de la sesión**, porque `01-definicion-producto.md:251` (R8) lo declara explícitamente "no persistido" y es de M2, y el **registro de ejecuciones en vivo**, que no aparece en la línea de la tarea y cuyo dueño natural es el motor de flujos. Tampoco hay columna para el token de sesión del portal: el portal es requisito de M2 (`01-definicion-producto.md:231`), su token lo acuña la CLI al levantarlo, y añadir la columna ahora sería guardar algo con forma de token sin nada que autenticar — cuando aterrice guardará un digest, nunca el token. `document_issue` sí entra aunque no esté en las seis palabras: `03-arquitectura.md:85` exige que un documento inválido quede **marcado** y atribuido a su último editor, y marcar necesita dónde.

**Herencia.** T-022 rellena las cinco tablas documentales y mantiene `document_fts` sincronizada en la inserción, escribiendo `document_id` con el ULID del documento —nunca un `rowid`— (el borrado ya lo cubre el trigger); las columnas de atribución de `document_issue` tienen valor por defecto vacío para que detectar un documento inválido nunca dependa de que git sea contestable en ese instante. T-023 tiene ya el `Reset()` que necesita, pero el invariante completo requiere además el repoblado de T-022. Los catálogos de `notification.level`, `notification.category`, `session.state` y `project_lock.holder_kind` quedan como TEXT abierto —mismo trade-off que `requiredCapabilities`— porque cerrarlos exigiría adivinar el catálogo de la tarea que los posee. **Y queda vivo el residual de T-020**: `Repository` sigue sin locks, y `LocalDB` no se los da todavía; las escrituras concurrentes al mismo artefacto siguen siendo último-en-escribir-gana hasta T-031. En la misma línea, y anotado por la revisión: el campo `LocalDB.db` se escribe en `Reset()` y se lee en `DB()` sin sincronizar, así que un llamador que ignore el contrato del comentario de tipo tendría una carrera de datos sobre el campo, no solo un uso-después-de-cerrar. No se pone un mutex ahora a propósito: protegería el acceso al campo pero no impediría que un `Reset()` cierre el handle que otro acaba de obtener, así que daría confianza falsa a cambio de maquinaria; el sitio donde se resuelve de verdad es T-031, que es quien posee la serialización entre procesos.

**Pruebas.** `go test -race -count=1 ./store/...`, con `store/localdb_test.go` cubriendo: bootstrap de una base nueva y creación de `.atrio/`; reapertura que **no** reconstruye; reconstrucción ante generación ajena y ante una base sin estampar con tablas de otro; borrado de los sidecars al reconstruir; `Reset()` que vacía todas las tablas recorriendo `sqlite_master` en vez de una lista escrita a mano, para que una tabla nueva quede cubierta sola; los seis nombres de directorio incómodos con la aserción de ruta exacta y de los dos pragmas; los pragmas verificados sobre dos conexiones simultáneas del pool y sobre el efecto real de la cascada entre conexiones distintas; `STRICT` rechazando un tipo equivocado; el `CHECK` del catálogo de relaciones; el trigger de FTS y la cascada; unicidad de `document.path`; `match` y `snippet`; la atomicidad del bootstrap con esquema inyectado que falla a mitad; la clasificación de cada tabla contra un mapa escrito de forma independiente en el test; los patrones del `.gitignore`; una raíz relativa resuelta contra el directorio de trabajo y no contra el raíz del sistema; el modo 0600 sobre los tres archivos —omitido en Windows con motivo nombrado, porque allí `os.Chmod` solo mueve el atributo de solo lectura—; el estampado de generación revertido por `rollback`; un `Reset()` fallido que deja un handle cerrado y no uno que aparente funcionar; y uso concurrente para que `-race` tenga qué mirar. La revisión mutó tres de ellos para comprobar que no son vacíos: añadir una tabla sin clasificar, quitar los patrones nuevos del `.gitignore` y volver a la concatenación del DSN hacen fallar al test que dice cubrirlos. `internal/archtest` sigue en verde. Cross-compile de `store/` verificado a mano en las cinco plataformas con `CGO_ENABLED=0`, porque `make build-all` **sigue sin alcanzar `store/`**: `cmd/atrio` no lo importa todavía.

## Bloque 3 — Git (`gitops/`)

**T-030 · Envoltura segura de git** *(estado: **completada**, depende de T-001)*
Detección de binario y versión mínima, invocación por arrays (sin shell), parseo `--porcelain`. Validación/solicitud de identidad (user.name/email) con bloqueo al primer uso.

Alcance estrictamente el paquete `gitops/`: detección + versión mínima, la primitiva de invocación segura, `git status --porcelain=v1` y la identidad. Worktrees/ramas (T-031), changelog (T-032) y todo lo de `store/`/`core/` quedan fuera, sin tocarlos.

**Versión mínima: 2.30.0, cota inferior únicamente.** ADR-004 deja la cifra a la implementación ("dependencia de versión mínima de git a declarar"). Se elige 2.30.0 (diciembre 2020) por ser lo bastante antigua para estar disponible en los repositorios por defecto de distribuciones Linux LTS aún en uso, y lo bastante moderna para que `--porcelain=v1 -z` y `git config --get` se comporten exactamente como documentado —ambos llevan estables mucho más tiempo que ese piso—. A diferencia de los adaptadores de proveedor (§7, que declaran un *rango* de versiones soportadas porque el proveedor es un objetivo móvil de terceros), git es un prerrequisito del sistema: solo cota inferior, sin techo. `MinimumVersionMajor/Minor/Patch` son las constantes literales que pide la tarea; `MinimumVersion` es el valor `Version` derivado para comparar directamente contra `Binary.Version`.

**`--porcelain=v1 -z`, no v1 a secas.** La tarea permitía v2 si se justificaba; se justifica quedarse en v1 pero añadiendo `-z`: sin `-z`, git aplica su citado estilo C a rutas "inusuales" (espacios, comillas, bytes no-ASCII), lo que habría obligado a reimplementar esas reglas de citado como un segundo lugar, más difícil de auditar, donde el "parseo total" podía fallar en silencio. Con `-z`, cada registro llega verbatim y terminado en NUL — verificado empíricamente contra git 2.50.1 con archivos con espacios, un rename y una eliminación antes de escribir el parser, no asumido de la documentación. Se añade además `--untracked-files=normal`: sin fijarlo, `status.showUntrackedFiles=no` en la configuración del usuario haría que `Status` omitiera archivos sin seguimiento en silencio — quien use `Status` para decidir si un worktree está limpio vería "limpio" sobre un árbol que no lo está, exactamente el hueco que el parser total existe para evitar. Verificado que las variantes de configuración (`status.branch`, `status.short`) no inyectan una cabecera `##` en el formato porcelain v1, así que no hace falta `--no-branch` defensivo.

**El parser es total: `patternProperties`-como para el estado, en vez de aceptar cualquier byte.** `parsePorcelainV1Z` exige el prefijo `"XY "` de tres bytes, valida X e Y contra el catálogo documentado (` MADRCUT`, más los pares `??`/`!!` que deben aparecer casados), y consume el campo de origen adicional para rename/copy — cualquier desviación es un error explícito, no una línea descartada. `T` (typechange, p. ej. un archivo reemplazado por un symlink) se incluyó tras una revisión: es un estado normal del repositorio, no un caso límite, y omitirlo habría convertido una llamada rutinaria a `Status` en un fallo — verificado con un symlink real antes de escribir la fixture. El caso "línea malformada" pedido por la tarea se cubre en dos frentes: un test de función pura contra secuencias de bytes sintéticas (siete variantes) y la integración contra un repo real con seis estados simultáneos (altas en stage, modificación con y sin stage, borrado sin stage, rename en stage, sin seguimiento).

**Identidad: precedencia completa, no solo `--local`.** `Identity` lee `git config --get user.name/user.email` sin forzar `--local`, es decir la misma cadena local→global→sistema que usaría `git commit`. Coincide con la lectura de la spec ("identidad = configuración git del proyecto"): el proyecto puede heredar una identidad global del desarrollador, y eso es válido. Un valor presente pero vacío (`git config user.name ""`, que sale con código 0) se trata igual que ausente — ninguno de los dos es una atribución utilizable. El mensaje de bloqueo nombra el comando exacto (`git config user.name/email "..."`) y aclara que sin `--global` queda scopeado a este repositorio, con la alternativa `--global` mencionada explícitamente para quien quiera identidad de máquina.

**Superficie pública deliberadamente angosta.** `Binary`, `Locate`/`LocateNamed`, `Version`, `StatusEntry`, `Identity` y los errores centinela (`ErrGitNotFound`, `ErrVersionTooOld`, `ErrVersionUnreadable`, `ErrIdentityIncomplete`) son lo único exportado. La primitiva de invocación (`runRaw`/`run`, `runError`) queda sin exportar a propósito: ningún llamador externo al paquete puede hoy construir una invocación git arbitraria, ni por accidente ni por descuido — la superficie pública no tiene ningún punto donde un valor externo se convierta en un argumento de git. Es la lectura más fuerte posible de "diseña la API de forma que construir un comando inseguro sea difícil": no difícil, imposible desde fuera del paquete en el estado actual. T-031 y T-032 viven en el mismo paquete (`gitops/doc.go` ya declara worktrees/ramas y commit/push gobernado como sus responsabilidades), así que ampliarán esta primitiva *dentro* del paquete — evolución esperada, no una excepción a nada decidido aquí.

**Hueco documentado, no cerrado: herencia de entorno.** `runRaw` deja `cmd.Env` sin fijar, por lo que hereda el entorno del proceso llamante tal cual — es lo que permite a los tests aislar la resolución de configuración de git con `t.Setenv` (`GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL`), pero también significa que unas `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE` ambientales podrían redirigir una invocación fuera de `dir`. Queda anotado en el código para quien primero necesite una garantía de directorio más fuerte que "sin shell interpolado" — T-031 es el dueño natural de esa decisión.

**Fake git compilado, no un script.** El helper de pruebas (`gitops/testdata/fakegit`) es un binario Go de ~60 líneas controlado por variables de entorno (versión simulada, volcado de argv, código de salida), compilado en `TestMain` antes de cualquier test. Se descartó un script de shell: no habría corrido igual en Windows, donde `exec.LookPath`/`exec.Command` no interpretan `#!/bin/sh`, y la matriz de CI incluye `windows/amd64`. `testdata/` es la ubicación establecida por el proyecto para código de soporte que `go build`/`go vet`/`go list ./...` deben ignorar pero que golangci-lint sí recorre (confirmado empíricamente: los `nolint` de `fakegit/main.go` se reportarían como no usados si el linter no lo escaneara, y no lo hicieron).

**Aislamiento de configuración en los tests de identidad y estado, real en todo el rango soportado.** La primera versión aislaba solo con `GIT_CONFIG_NOSYSTEM=1` + `GIT_CONFIG_GLOBAL` apuntando a una ruta inexistente — revisión detectó que `GIT_CONFIG_GLOBAL` existe recién desde git **2.32.0**, por debajo de `MinimumVersion` (2.30.0): en un git 2.30/2.31, que `Locate` acepta sin más, esa variable se ignora y la configuración de la máquina se cuela sin aviso. Se añade `HOME`/`USERPROFILE`/`XDG_CONFIG_HOME` apuntando a un directorio vacío de `t.TempDir()`, que es el mecanismo por el que git descubre `$HOME/.gitconfig` o `$XDG_CONFIG_HOME/git/config` desde mucho antes del piso de versión de este paquete — verificado con un repo real y `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_NOSYSTEM` explícitamente ausentes, que el aislamiento por `HOME` basta por sí solo. Los dos mecanismos quedan superpuestos a propósito, no uno sustituyendo al otro. Esto aísla cada repo temporal de lo que tenga configurado la máquina donde corren los tests, incluido el `core.autocrlf=true` que los runners de Windows de GitHub Actions traen en la configuración de sistema. Se aplica también a los tests de `Status`, no solo a los de `Identity`: un `autocrlf` o `showUntrackedFiles` ambiental podría alterar el conteo exacto de entradas que esos tests verifican, en un solo runner de la matriz. `realGit` (helper de test) falla cerrado (`t.Fatalf`) si no encuentra un git real, en vez de `t.Skip` — la misma postura que `internal/archtest` documenta para su propia dependencia de `go list`: un `Locate` roto no debe traducirse en que toda la suite de `Status`/`Identity` reporte verde sin haber probado nada.

**`IsIgnored()` no se añadió.** `Status` nunca pasa `--ignored`, así que el par `!!` no puede aparecer en su salida real; un método que solo podría devolver `false` es superficie pública inerte, y la virtud declarada de este paquete es una API deliberadamente angosta. El **parser** sí reconoce `!!` como par válido — su totalidad frente a cualquier entrada es una propiedad distinta y deseable, independiente de qué banderas pase `Status` hoy.

**Herencia para T-031: disciplina de `--` y de pathspec.** Hoy la inyección de argumentos es inalcanzable por diseño: ninguna función pública de este paquete acepta un valor del llamador que termine como elemento de `args` — `Status` e `Identity` solo construyen subcomandos con literales fijos. Eso deja de ser cierto en cuanto T-031 empiece a pasar nombres de rama y rutas influidos por el usuario hacia el primitivo interno (`run`/`runRaw`): el array de argumentos impide la inyección de *shell*, pero no protege por sí solo contra un valor que empiece por `-` y que git interprete como una opción en vez de como un nombre de rama o una ruta. T-031 tiene que decidir, en el punto donde el primer valor externo entre a `args ...string`, entre separador `--` (para el caso general) o el prefijo `./` en rutas (el idiom de pathspec de git) — no es una elección que este paquete resuelva por adelantado sin un caso de uso concreto delante.

**Ambigüedad reportada, no resuelta por adivinanza.** La tarea menciona "fuera de rango" al hablar de la versión mínima; se interpretó como "por debajo del mínimo" (sin techo), documentado arriba — no hay otra lectura consistente con que ADR-004 solo pida declarar un mínimo.

Ficheros: `gitops/{version,binary,run,status,identity}.go` y sus `_test.go`, más `gitops/testdata/fakegit/main.go`. `make verify` (fmt-check + vet + lint + `-race`) y `make build-all` pasan limpios.

Creación `{task|bug}/{ulid-corto}-{slug}`, worktree por tarea, limpieza determinística de huérfanos, commit/push gobernados.

## Bloque 4 — Dominio (`core/`)

**T-040 · Entidades y máquinas de estado** *(estado: **completada**, depende de T-010)*
Ciclo de vida de tarea completo (construcción → ready_for_dev → ejecución → bucle por ambiente → definitivos; bugs desde triage), decisiones inmutables con reemplazo, bitácora append-only. Sin I/O: lógica pura testeable.

Cinco archivos en `core/` (`actor.go`, `task.go`, `environment.go`, `decision.go`, `log.go`), sin ningún import del módulo — `internal/archtest` lo verifica — y sin ninguna dependencia nueva en `go.mod`. Los tipos son propios del dominio, no un espejo de los esquemas de `schemas/`: mapear JSON↔Go es de T-020, así que `Task`, `Decision` y `LogEntry` solo llevan los campos que una regla de esta tarea necesita, no la forma completa del artefacto.

**El grafo de transiciones es una decisión de esta tarea, no de la spec.** El backlog delega expresamente "el orden legal de transiciones es tuyo"; `01-definicion-producto.md:142-160` describe las fases pero no el grafo arista por arista. Se fijó así, y cada arista no obvia tiene una razón:
- `draft → ready_for_dev` (construcción) y `ready_for_dev → in_progress` (arranque de ejecución).
- `blocked` es alcanzable solo desde `in_progress` e `in_review`, nunca desde `ready_for_dev` ni desde `deploying`/`testing`: la propia spec agrupa "desarrollo, bloqueo, code review" como una sola fase (sección 8, fase 2), y el bucle por ambiente es una fase aparte con nombre propio (fase 3). Un despliegue bloqueado por una respuesta de operaciones pasa primero por `testing → in_progress` y desde ahí a `blocked`; es un salto extra deliberado, no un hueco.
- `blocked` siempre vuelve a `in_progress`, sin importar si el bloqueo se originó en `in_progress` o en `in_review`: reanudar significa retomar el trabajo, no reingresar a revisión sin pasar por él.
- `in_review` tiene tres salidas: de vuelta a `in_progress` (cambios solicitados), a `deploying` (abre el bucle por ambiente) o a `completed` — esta última, **condicionada**; ver el bloque siguiente.
- El bucle (`deploying ↔ testing`) avanza con `testing → deploying` (siguiente ambiente), retrocede con `testing → in_progress` (prueba fallida) y cierra con `testing → completed` — también condicionada. El grafo no conoce el orden de `environments[]` del proyecto —eso vive en otro artefacto—, así que `testing → deploying` es legal sin condición: recorrer el bucle una vez por ambiente declarado y detenerse en `closureEnvironment` sigue siendo responsabilidad de quien sí tiene esa lista (el motor de flujos o la CLI, T-070/T-080). Queda anotado como residual explícito en el propio comentario del código, no como una promesa implícita.
- `cancelled` es alcanzable desde cualquier estado no definitivo: abandonar una tarea es legal en cualquier punto antes de cerrarla.
- `triage` nunca es destino de ninguna transición —solo se nace ahí (`InitialState`/`ValidateBirth`)— y como origen solo es legal para `type: bug`; un `task` en `triage` es irrepresentable en el grafo, coherente con la regla ya congelada en el esquema.
- Un bug se triagea hacia el mismo grafo que una tarea vía `triage → ready_for_dev` (encolado normal) o `triage → in_progress` (directo a trabajo); desde ahí sigue las mismas reglas que cualquier tarea.

**El cierre es condicional, no incondicional — decisión del usuario tras escalar la contradicción.** `task.schema.json:71` deja `closureEnvironment` opcional, y la primera versión de esta tarea resolvió eso con `in_review → completed` sin condición, lo cual dejaba a **cualquier** tarea —tuviera o no ambiente de cierre declarado— la opción de saltarse el bucle entero. Escalada la contradicción, la regla que quedó es la que compara el propio dato de la tarea, que ya vive en memoria y sigue siendo dominio puro:
- **Sin `closureEnvironment`**: `in_review → completed` es legal — la salida para un cambio que no despliega (documentación, por ejemplo).
- **Con `closureEnvironment`**: `in_review → completed` es **ilegal**; esa tarea cierra solo por el bucle, que es donde `01-definicion-producto.md` §8 exige confirmación humana por ambiente, y permitirle saltárselo vaciaría esa garantía.
- La mitad simétrica, para no dejar la puerta de al lado abierta: **`testing → completed` es legal solo cuando `CurrentEnvironment` de la tarea coincide con su `ClosureEnvironment`**. El campo significa dónde se considera cerrada; completar desde las pruebas de un ambiente distinto lo contradiría.

Esto obligó a cambiar la firma de `CanTransition`, de `(TaskType, TaskState, TaskState)` a `(Task, TaskState)`: el par de estados más el tipo ya no basta para decidir las dos aristas de cierre, que necesitan `ClosureEnvironment` y `CurrentEnvironment` de la propia tarea. Pasar la tarea completa —en vez de solo esos dos campos sueltos— fue la opción elegida por dejar la firma más honesta: ningún llamador puede pedir una transición sin aportar el dato completo que la decide, y `ApplyTransition`/`ValidateTaskUpdate` ya tenían la tarea a mano de todos modos.

**Bloqueante real, reproducido empíricamente por revisión: la regla de cierre no llegaba a `ValidateTaskUpdate`.** `CanTransition(previous, next.State)` evalúa la arista con los campos de ambiente de `previous`. Como una misma escritura puede cambiar `State` y esos campos a la vez, y `store` (T-020) es exactamente el punto de entrada donde eso ocurre, se colaba un cierre ilegal en cualquier dirección: `previous = {in_review, closure: ""} → next = {completed, closure: "prod"}` pasaba —`previous` no declaraba ambiente, así que su versión de la regla decía "cierre directo legal", y lo que `next` declarase de más nunca se miraba—, dejando una tarea `completed` con cierre en `prod` sin haber pisado el bucle, e irreparable por ser estado definitivo. El arreglo obvio de evaluar contra `next` en vez de `previous` tiene un agujero simétrico y no cierra nada, solo invierte el sentido del contrabando: `previous = {in_review, closure: "prod"} → next = {completed, closure: ""}` pasaría con esa versión, porque bastaría **borrar** el campo en la misma escritura para que `next` diga que el cierre directo es legal.

La regla que sí cierra ambos sentidos exige que la arista siga siendo legal bajo las dos versiones, no bajo una sola: `ValidateTaskUpdate` evalúa `CanTransition(previous, next.State)` (ya estaba) **y además** `CanTransition` sobre una tarea con el estado de origen de `previous` pero los campos `ClosureEnvironment`/`CurrentEnvironment` de `next` — la misma arista, juzgada con los datos de la otra versión. Ninguna escritura que cambie esos campos a la vez que el estado puede colarse ya, porque tendría que superar la regla de cierre calculada con los valores de antes **y** con los de después. Cambiar `closureEnvironment` mientras la tarea sigue en curso —sin completar en la misma escritura— sigue siendo legal sin restricción: la puerta solo se activa cuando el estado destino es `completed`, que es la única transición cuya legalidad depende de esos campos.

**`CurrentEnvironment` deja de cambiar por asignación directa.** Nada en el dominio gobernaba antes cuándo ni cómo cambiaba ese campo —el propio `TestEnvironmentLoop_FullWalk` lo demostraba, asignándolo entre llamadas a `ApplyTransition`—, y es el mismo vector que el bloqueante anterior: un campo que decide legalidad y que cualquiera puede tocar sin pasar por el dominio. Se añadió `Task.EnterEnvironment(environment, by, at, reason)`: entrar en `deploying` es entrar *para un ambiente concreto*, así que ese ambiente pasa a ser argumento de la operación —construida sobre `ApplyTransition`, que sigue decidiendo si entrar en `deploying` es legal desde donde esté la tarea— en vez de un campo que el llamador asigna por su cuenta después. Cubre tanto la primera ronda del bucle (`in_review → deploying`) como cada ronda siguiente (`testing → deploying`), con el mismo método. El test del bucle completo se reescribió para recorrerlo por esta API, no por asignación.

**Decisión deliberada, no descuido: `in_review → deploying` sigue siendo legal sin `closureEnvironment` declarado.** Es semánticamente laxo —se puede entrar al bucle sin saber todavía dónde se cierra— pero cerrarlo bloquearía un flujo legítimo: un equipo que empieza a desplegar y decide el ambiente de cierre después. No genera callejón sin salida: la retirada por `in_progress`/`in_review` sigue disponible en cualquier punto del bucle, y `testing → completed` de todos modos exige `ClosureEnvironment` no vacío y coincidente con `CurrentEnvironment`, así que una tarea que entra al bucle sin declarar cierre simplemente no puede completar por esa vía hasta declararlo.

**Modelado deliberadamente ausente: una sola arista por evento, no el bucle completo como unidad.** `CanTransition` no sabe que está "en un bucle": cada llamada evalúa un paso, y quien encadena los pasos por cada ambiente es el llamador. Es la misma frontera que separa esta tarea de T-070; el residual sobre el orden de `environments[]` queda exactamente donde estaba.

**`TaskType` deja de tragarse valores desconocidos en silencio.** `DecisionStatus` ya rechazaba un valor fuera del catálogo cerrado; `TaskType` no lo hacía —`InitialState("basura")` devolvía `draft` sin protestar—, una asimetría que no tenía justificación una vez señalada. Se añadió `TaskType.Valid()`, y tanto `ValidateBirth` como `CanTransition` lo consultan primero y fallan cerrado ante un tipo no reconocido, en vez de tratarlo como si fuera `task`. `InitialState` en sí queda total (con `draft` como reverso por defecto) porque `ValidateBirth` es quien carga con la comprobación explícita — la misma división que ya tenía `ValidateDecisionUpdate` frente a un `DecisionStatus` inválido.

**`ValidateBirth` — refuerzo en el dominio de una regla que el esquema ya expresa, y no una contradicción.** `schemas/README.md` asigna "solo un bug nace en `triage`" al esquema (`task.schema.json`, vía `if/then` sobre `type`); `NewTask` no puede violarla por construcción, porque deriva el estado de nacimiento del tipo. `ValidateBirth` se expone además como predicado puro porque la tarea pide explícitamente el caso de prueba "bug naciendo fuera de triage", y porque un consumidor en memoria —un flujo que acuña un bug a mitad de ejecución, antes de que exista ningún JSON que validar— necesita la misma garantía sin pasar por el esquema. Es refuerzo en dos capas, no duplicación con ambigüedad: el esquema valida el documento serializado, esto valida la construcción en memoria. Lo que **no** se implementó, porque es la otra mitad de esa misma fila y ya está resuelta por el esquema, es la exigencia de `originTaskRef` para un bug o su prohibición para una tarea.

**`Blocker`/`BlockedBy` dejan de ser superficie inerte: el dominio los comprueba, al construir y al actualizar — decisión del usuario.** Un tipo modelado que ninguna operación ni ningún test ejercita no se sostiene en un contrato nuevo, así que se decidió dotarlo de comprobación real en vez de retirarlo. `ValidateBlocked(t Task)` exige que una tarea en `blocked` nombre al menos un bloqueador; es la misma clase de refuerzo en dos capas que `ValidateBirth` —`schemas/README.md` ya asigna "`blockedBy` obligatorio en `blocked`" al esquema— aplicada aquí a un tipo que antes no tenía ningún guardián propio. Se llama desde dos sitios, no uno: `ApplyTransition` la exige sobre la tarea resultante antes de devolverla (así "al construir" un `blocked` sin bloqueador falla en el momento de construirlo, no después), y `ValidateTaskUpdate` la exige sobre `next` sin condicionarla a que el estado haya cambiado (así "al actualizar" también atrapa a una tarea que sigue `blocked` pero pierde su único bloqueador en la nueva versión, que es tan ilegal como no haberlo tenido nunca). Se dejó deliberadamente **fuera** de `CanTransition`: si algo bloquea una tarea es información nueva en el momento exacto de la transición, no un dato ya estable en la tarea de origen como sí lo son `ClosureEnvironment`/`CurrentEnvironment` para el cierre — meterlo en el grafo habría acoplado dos preguntas distintas (¿es esta arista legal? vs. ¿es esta tarea internamente consistente estando bloqueada?) en una sola función.

**`ValidateTaskUpdate` es el punto de entrada que compara dos versiones, y cubre cuatro reglas, no una.** La tabla del README solo nombra la inmutabilidad de estados definitivos, pero dejar la función a medias habría hecho que un cambio de estado entre dos versiones que no pasara por `ApplyTransition` (el camino que tomará `store` al validar una escritura entrante en T-020) quedara sin verificar el orden legal, sin la regla de cierre bajo ambas versiones (el bloqueante de arriba) ni la consistencia de `blockedBy`. Además de la inmutabilidad de estados definitivos: si el estado cambia entre `previous` y `next` y `previous` no es definitivo, el cambio tiene que ser una arista legal del grafo evaluada con los campos de ambiente de `previous` **y**, por separado, con los de `next`; y `next` tiene que pasar `ValidateBlocked` sin importar si el estado cambió. `ApplyTransition` sigue siendo el camino feliz para construir una tarea paso a paso —ahí `previous`/`next` comparten los mismos campos de ambiente por construcción, así que la doble comprobación no le hace falta—; `ValidateTaskUpdate` es el guardián para cualquier otro camino que llegue a las dos versiones ya hechas, que es exactamente donde el bloqueante vivía.

**Decisiones: contenido inmutable, con una sola mutación posible y verificada por comparación completa.** `ValidateDecisionUpdate(previous, next)` compara ambas versiones campo a campo (`reflect.DeepEqual` sobre una copia con `status`/`supersededBy` vaciados) y solo permite dos resultados: sin cambio de contenido, o la transición `active → superseded` con `supersededBy` no vacío y sin ningún otro campo tocado. Una decisión ya `superseded` rechaza cualquier cambio posterior, incluida la reasignación de `supersededBy` o un intento de "revivirla" a `active`: ninguna de las dos está en la spec como legal, y dejarlas pasar por descuido de un caso límite habría sido peor que no cubrirlo. Un `status` fuera del catálogo cerrado (`""`, o cualquier cadena que no sea `active`/`superseded` — `DecisionStatus` es un string con nombre, no un enum cerrado en tiempo de compilación) cae en una rama de rechazo explícita en vez de colarse por la comparación de igualdad.

**Bitácora append-only como diseño de API, no como comprobación en tiempo de ejecución.** `Log` guarda sus entradas en un slice no exportado; `Append` devuelve un `Log` nuevo sin tocar el receptor, y `Entries` devuelve una copia. No existe ningún método que permita alcanzar una entrada ya añadida y modificarla: la disciplina append-only es una propiedad de la superficie del tipo, verificada por los tests con la misma técnica que usa el resto del código (copiar y comprobar que la copia no se contamina), no una validación que compare bytes contra el filesystem — eso es de T-020, tal como fija `schemas/README.md`.

**`LogPayload.Capability` se deja como `string` desnudo, sin acuñar el enum de las siete categorías.** El catálogo de categorías de permiso es responsabilidad de T-041 (motor de permisos); acuñarlo aquí habría sido invadir esa tarea sin necesidad, ya que ninguna regla de T-040 lo consulta.

**Grafo de estados verificado por producto cartesiano completo, no por muestreo.** `TestCanTransition_FullStateGraph` recorre 2 tipos × 9 estados no-`triage` × 9 estados no-`triage` × 3 casos de ambiente (sin `closureEnvironment`; con `closureEnvironment` y `currentEnvironment` coincidente; con `closureEnvironment` y `currentEnvironment` distinto) contra una tabla de aristas y una réplica de la lógica condicional escritas de forma independiente en el test (no derivadas llamando a `CanTransition`), siguiendo la misma disciplina que `internal/archtest` e `internal/citest`: "sincronizado por un test, no por un comentario". Una arista añadida o borrada por error en `taskTransitions`, o una de las dos condiciones de cierre aflojada, sin el cambio equivalente en el test, rompe la suite. `triage` se aisló en `TestCanTransition_Triage` porque su legalidad depende también del tipo; un tipo fuera del catálogo, en `TestCanTransition_UnknownType`. Las cuatro escenas que motivaron la regla de cierre —legal sin ambiente declarado, ilegal desde revisión con ambiente declarado, legal desde pruebas en el ambiente de cierre, ilegal desde pruebas en otro— quedan además nombradas una a una en `TestCanTransition_ClosureGating`, redundante a propósito con el producto cartesiano: como criterio de aceptación legible, no solo como caso cubierto entre miles.

**Límite conocido de `allTaskStates`, corregido en el comentario para no prometer de más.** El comentario original afirmaba que la tabla independiente protegía contra un estado nuevo añadido al enum y nunca añadido a la lista; eso no es cierto — Go no da reflexión sobre constantes, así que un `TaskState` nuevo que nadie agregue a `allTaskStates` queda fuera del producto cartesiano sin que ningún test lo note. El comentario se reescribió para decir exactamente lo que sí protege (deriva entre aristas de estados ya listados) y señalar el hueco como disciplina de revisión, no como garantía de test — el mismo tratamiento que `CLAUDE.md` ya da a los huecos conocidos de `internal/archtest`.

**Regresión específica para el bloqueante, en las dos direcciones y sobre las dos aristas de cierre.** `TestValidateTaskUpdate` gana seis casos dedicados: añadir `closureEnvironment` y quitarlo, ambos en la misma escritura que completa desde revisión; cambiarlo a un ambiente nunca probado en la misma escritura que completa desde el bucle; los dos cierres legítimos correspondientes (sin ambiente en ninguna versión; con el mismo ambiente coincidente en ambas); y que cambiar `closureEnvironment` a mitad de tarea sin completar en la misma escritura siga sin bloquearse. Es la combinación que el 100 % de cobertura de sentencias no veía: cobertura de líneas no es cobertura de combinaciones de campos entre dos versiones.

**Bucle por ambiente probado con valores reales y por la API del dominio, no por asignación directa.** `TestEnvironmentLoop_FullWalk` recorre tres ambientes declarados (`dev`, `staging`, `prod`) entrando a cada uno con `EnterEnvironment` —no asignando `CurrentEnvironment` a mano—, comprueba que el orden recorrido coincide con el declarado, cierra desde `testing` exactamente cuando `CurrentEnvironment` es `prod` —la arista condicionada que la regla de cierre exige, no una coincidencia— y valida `closureEnvironment` contra `walked`, la lista que el propio bucle construyó, no contra el literal de entrada del test: el comentario anterior prometía comprobar "los ambientes que recorrió" y la aserción comprobaba el literal, un segundo comentario optimista en esta tarea que quedó corregido junto con el código, no solo con la prosa. `TestEnterEnvironment` cubre el método por separado: ambiente vacío rechazado, ambiente nombrado fija `CurrentEnvironment` al entrar en `deploying`, y la legalidad de entrar en `deploying` en sí sigue dependiendo del grafo de estados.

**Cobertura**: 100 % de sentencias en `core` (`go test -cover`), sin exenciones.

**Residual explícito para T-070/T-080.** Ningún consumidor llama todavía a estos predicados — `core` y `store` no se importan entre sí en esta ronda, tal como pide la tarea—. El primero en cablear ambos será el motor de flujos o la CLI (T-070/T-080), que además es quien tiene que recorrer `environments[]` del proyecto en orden y detenerse en `closureEnvironment`, ya que `core` deliberadamente no conoce esa lista.

**Herencia explícita para quien construya el mapeo JSON↔dominio.** Nada ata mecánicamente los enums de `core` (`TaskState`, `TaskType`, `BlockerKind`, `DecisionStatus`, `LogEventType`) a los enums equivalentes de `schemas/` — `core` no puede importar `schemas/` sin violar ADR-016, así que no hay ningún test posible dentro de este paquete que lo verifique. Una edición futura de `task.schema.json` que añada, quite o renombre un valor del enum `state` derivaría en silencio de `core.TaskState` hasta que algo lo note en tiempo de ejecución. Su sitio natural es la tarea que construya el mapeo JSON↔Go (candidata: T-020, que ya es quien decidió no vivir en `core` por la regla de dependencias), con un test que recorra ambos catálogos y falle si difieren — el mismo patrón de "sincronizado por un test" que el resto del proyecto usa para pares que no pueden vivir en el mismo paquete.

## Riesgos de implementación a vigilar

1. **T-053 es la tarea de mayor incertidumbre**: el transporte de permisos vía mecanismos de Claude Code depende de capacidades de terceros que evolucionan. Hacer *spike* técnico temprano (antes de cerrar el diseño fino de T-050) para validar viabilidad del arbitraje en el core.
2. **T-011 congela API pública**: revisar dos veces antes del primer tag.
3. **Cross-compile limpio**: cualquier dependencia con CGo lo rompe; la matriz de CI (T-002) lo detecta desde el inicio.
4. **Marca del nombre Atrio**: la colisión con Atrio Inc. (atrio.io) debe validarse legalmente antes del primer release público; el naming técnico (`atrio`, `.atrio/`) ya está fijado.
